# 来源可信度评估规则

技术选型中，来源互相矛盾是常态。本文件定义可信度分级与处理规则，确保报告中每个关键论断都标注来源等级，矛盾被呈现而非被掩盖。

---

## 一、五级可信度分档

| 等级 | 来源类型 | 典型示例 | 使用规则 |
|---|---|---|---|
| L1 最高 | 官方一手资料 | 官方文档、官方白皮书、官方发布说明（changelog/release notes）、官方 issue tracker 中的维护者确认 | 用于确认"有什么功能、版本边界、官方立场"；对官方自称的性能优势保持警惕（见降级规则） |
| L2 高 | 可复现的第三方基准 | 知名基准套件（sysbench、TPC 系、js-framework-benchmark 等）的第三方执行结果、有完整测试条件说明的技术公司工程博客 | 必须核对测试条件（版本、硬件、数据集）与本次场景的匹配度 |
| L3 中 | 生产实践经验 | 可考证的公司技术博客复盘、会议分享（含故障复盘）、知名工程团队的迁移报告 | 注意样本偏差：分享者往往极端满意或极端不满；单案例不可外推 |
| L4 低 | 社区一般讨论 | Stack Overflow 回答、Reddit/V2EX/知乎讨论、个人博客、聚合类对比文章 | 仅用于发现线索（"有人遇到过 X 问题"），不能作为结论依据，需回溯到 L1-L3 佐证 |
| L5 不可用 | 来源不明或明显有偏见 | 无署名转载、AI 生成内容农场、厂商软文伪装成的第三方评测、无法考证出处的截图/数字 | 不引用。若其中含有独家线索，标注"待证伪"并尝试溯源 |

### 强制降级规则

以下情况在原等级基础上**降一档**：

- **利益相关**：厂商发布的涉及自身产品的对比（如 Redis Inc 发布的 Redis vs X），即使是技术内容也降档
- **带货性质**：培训机构、外包公司发布的选型文章（倾向推荐人才供给多的方案）
- **版本错配**：论断基于的版本与当前评估版本跨了 ≥2 个大版本
- **条件缺失**：基准数据没有说明测试条件，无法判断可比性

## 二、CRAAP 测试

对每个关键来源执行五问（Currency / Relevance / Authority / Accuracy / Purpose）：

1. **时效性（Currency）**：发布/更新时间是什么？基于哪个版本？近 12 个月内？
2. **相关性（Relevance）**：测试/讨论的场景与本次决策的负载特征是否匹配？（读多写少 vs 写密集，小团队 vs 大集群）
3. **权威性（Authority）**：作者是谁？是否有该领域的可考证经验？是否利益相关方？
4. **准确性（Accuracy）**：论断是否有数据/代码/复现步骤支撑？其他来源能否交叉验证？
5. **目的性（Purpose）**：写作目的是分享经验还是推广产品/课程/招聘？

五问中"目的性"或"权威性"不合格的来源，直接降至 L4 或 L5。

## 三、时效性衰减规则

技术论断有保质期。按内容类型分别处理：

| 内容类型 | 有效窗口 | 过期处理 |
|---|---|---|
| 性能基准数据 | 12 个月或 1 个大版本（先到为准） | 必须标注"基于版本 X，当前版本已迭代"，并尝试找新版本数据替换 |
| 功能特性描述 | 至下一个大版本 | 与最新官方文档核对，以 L1 为准 |
| 生态/市场数据（下载量、招聘、采用率） | 12 个月 | 标注统计时点；趋势判断需至少两个时点数据 |
| 故障模式/运维经验 | 24-36 个月 | 检查是否已被新版本修复（翻 issue tracker 与 changelog） |
| 架构设计哲学、核心权衡 | 长期有效 | 可引用经典文献，但仍需确认该设计在当前版本未被重构 |

**硬性要求**：整体取证中近 12 个月的来源应占多数；若某关键维度只能找到过期来源，在报告"遗留不确定性"中声明。

---

## 四、来源矛盾处理流程

当来源互相打架时，按此流程处理：

1. **先查版本与条件**：多数"矛盾"其实是版本不同或测试条件不同造成的，尝试调和（"A 说 X 快，基于 v8 简单点查；B 说 Y 快，基于 v17 复杂查询——两者不冲突"）
2. **查利益相关方**：矛盾双方是否有立场差异（官方 vs 竞品 vs 独立第三方）
3. **无法调和时并列呈现**：在报告中写明"关于 Z，来源甲（L2，2025-10）认为…，来源乙（L2，2026-03）认为…，差异可能源于…"
4. **转化为 POC 验证项**：对决策有实质影响且无法调和的矛盾，列入 POC 验证计划的测试项

**禁止**：擅自采信一方并隐藏另一方；用"多数来源认为"和稀泥而不说明分歧点。

## 五、报告中的标注格式

关键论断采用行内标注：

```
PostgreSQL 的 JSONB 支持 GIN 索引，可在嵌套 JSON 查询中使用索引加速
[来源: 官方文档, L1, 核对版本 17, 2026-01 访问]
```

简化短标注：`[L1/官方文档/v17]`、`[L2/第三方基准/2025-11]`。

报告末尾附完整来源清单：标题、URL、发布日期、访问日期、等级、降级原因（如有）。
