# Tech Tradeoff Analysis — 技术选型利弊分析

## 定位与原则

技术选型的痛点不是信息不够，而是信息碎片化、互相矛盾、缺乏系统化依据。本 Skill 的职责是**把利弊说清楚**，而不是替用户打分或做决定。

三条不可违背的设计原则：

1. **不打分**。禁止使用权重、1-5 分、星级、雷达图评分等量化手段。分数会制造虚假的精确感，掩盖真正的不确定性。用文字说清"什么条件下谁占优"。
2. **不站队**。每个维度下必须同时列出候选方案的优势、劣势、风险；若某个方案在某维度确实全面占优，也要说明占优的前提条件。
3. **边界清晰比能力泛化更重要**。遇到边界外请求，直接说明不适用并停下，不要勉强套用流程。

## 适用边界

**适用**：
- 开源/公开技术方案的横向对比（数据库、中间件、框架、语言运行时、云服务等）
- 候选方案有公开文档、社区讨论、第三方评测可供取证

**不适用于**：
- 非技术类决策（商业策略、组织架构、管理决策）
- 无法联网搜索取证的闭源产品内部细节、公司内部系统评估
- 需要替用户拍板的场景——本 Skill 输出决策依据，最终判断权永远属于决策者

## 四步工作流

### 第 1 步：需求锚定

在搜索任何东西之前，先追问硬约束。没有锚点的对比只是资料堆砌。

必须澄清的问题（用户没主动说就问）：
- **负载特征**：读写比例、QPS/并发量级、数据规模、延迟要求（p99 还是平均值）
- **团队现状**：现有技术栈、团队对候选方案的熟悉程度、可投入的运维人力
- **硬约束**：预算上限、合规要求、是否必须自托管、迁移窗口、与现有系统的集成点
- **决策时限**：这决定取证的深度——本周要结论就收窄来源范围做快查，季度规划则允许深挖

若用户拒绝回答或确实没有约束，记录"约束缺失"本身，并在报告中标注结论的置信度会因此降低。

### 第 2 步：联网取证

对候选方案分别取证，遵守以下纪律：

- **来源数量**：每个候选方案都被覆盖后，整体不少于 **3 个独立来源**（官方文档/白皮书、第三方基准测试、社区实战经验帖各自算独立来源；同一内容的不同转载不算）
- **时效性**：优先采用**近 12 个月**的数据。超过 12 个月的来源必须标注时间并说明可能过时的点（版本已迭代、性能数据基于旧版本等）。版本号必须写清——"PostgreSQL 17 的 JSON 性能"而不是"PostgreSQL 的 JSON 性能"
- **矛盾处理**：当来源互相打架（如官方基准 vs 社区实测），不要二选一，**并列呈现并分析矛盾原因**（测试条件不同、版本不同、利益相关方背书）
- **可信度标注**：每个关键论断标注来源及其可信度等级，分级规则见 [references/credibility.md](references/credibility.md)（五级分档 + CRAAP 测试 + 时效性衰减）

搜索策略建议：
- 中英文各搜一轮（中文社区与英文社区的经验常有差异，尤其涉及中国市场生态时）
- 组合关键词：`{方案A} vs {方案B} {年份}`、`{方案} benchmark {版本号}`、`{方案} production experience / 生产实践`
- 对厂商发布的对比文章自动降一档可信度（利益相关）

### 第 3 步：利弊分析

读取 [references/dimensions.md](references/dimensions.md) 中的通用对比维度清单（功能性、性能、稳定性、运维成本、生态成熟度、技术风险），按以下规则执行：

1. **按需裁剪**：六大维度是检查清单而非必答清单。根据第 1 步锚定的约束，选出与本次决策相关的维度，并为该决策补充特有维度（如数据库选型补充"JSON 支持/复制机制"，前端框架补充"招聘市场/学习曲线"）
2. **三维并列**：每个维度下，对每个候选方案同时写优势、劣势、风险（尚未发生但可能引爆的问题，如许可证变更、核心维护者流失）
3. **条件化表述**：用"在 X 条件下，A 优于 B，因为…"的句式，禁止"A 比 B 好"这类无条件结论
4. **退出成本单独成章**：评估每个方案被替换的代价——数据迁移难度、协议/格式锁定、团队技能沉没成本、生态绑定深度

### 第 4 步：结论输出

按 [references/output-templates.md](references/output-templates.md) 中的标准选型报告模板输出，核心结构：

1. **需求摘要**（第 1 步锚定的约束，含缺失项声明）
2. **候选方案速览**（版本、许可证、背后组织、一句话定位）
3. **分维度利弊对比**（每个维度：优势/劣势/风险 × 各候选方案，附来源可信度标注）
4. **来源矛盾点说明**（哪些论断存在来源冲突，冲突的可能原因）
5. **适用场景建议**（"若你的场景是 X，倾向 A；若是 Y，倾向 B"——场景化建议，不是排名）
6. **退出成本对比**
7. **遗留不确定性**（未能证实/证伪的关键问题，建议通过 POC 验证——POC 计划模板见 output-templates.md）

若用户需要沉淀决策，可追加输出 ADR（Architecture Decision Record）；若不确定性高，可追加输出 POC 验证计划。模板均在 references/output-templates.md 中。

## 质量自检清单

输出前逐项核对：
- [ ] 未出现任何分数、星级、权重、排名表
- [ ] 每个维度同时存在优势与劣势（除非明确说明该维度确实无实质差异）
- [ ] 每个关键论断有来源 + 可信度等级 + 数据时间
- [ ] 独立来源 ≥ 3，且近 12 个月来源占多数
- [ ] 存在来源矛盾时做了并列呈现而非擅自取舍
- [ ] 建议部分是"场景 → 倾向"的条件句，不是绝对结论
- [ ] 包含退出成本与遗留不确定性两节

## 验证场景

以下三个经典选型场景用于验证本 Skill 的输出质量。对每个场景，产出应达到右侧的最低质量标准：

| 场景 | 必须覆盖的关键差异点（验证用，非结论） |
|---|---|
| PostgreSQL vs MySQL | JSONB 与 GIN 索引 vs 生成列索引的实现差异；MVCC 实现（无回滚段 vs 回滚段）对高并发写的影响；物理流复制 vs binlog 逻辑复制；PostGIS 等扩展生态；各自占优的负载类型（复杂查询/HTAP vs 简单高频点查） |
| Redis vs Memcached | 数据结构丰富度（Strings/Hashes/Sorted Sets/Streams vs 纯字符串）；持久化能力（RDB/AOF vs 无/warm restart）；线程模型（单线程+I/O 线程 vs 多线程）对多核利用的影响；内存效率（Memcached 简单键值场景每 key 开销更低）；原生 Cluster vs 客户端分片 |
| React vs Vue | 生态规模与招聘市场（npm 下载量、企业采用率差异）；框架完整度（视图层库+生态拼装 vs 官方全家桶）；学习曲线与上手速度；性能不应被夸大为决定因素（两者都足够快，差异在架构与 DX）；中国市场的特殊生态位（Vue 中文生态与大厂采用） |

验证通过的标准：报告能让一个不了解细节的决策者说清楚"在什么条件下选哪个、代价是什么、还有哪些没搞清楚"，而不是得到一个分数或排名。
